# 后续开发与取舍评估

候选功能的可行性评估与实现边界。硬约束适用于所有条目，先读最后一节。
每项给出「做 / 缓做 / 不做」的结论与触发重评的条件；已完成的项移入文末记录。

## 一、文本选中与复制 —— 已完成（2026-11，实机验证过）

原状：只有「复制全部输出」「复制当前屏」两个整块入口，想复制一个 URL /
token 只能复制整屏再手动删。现由长按拖选覆盖，实测全项通过（adb 注入 +
搜狗剪贴板栏第三方印证，见 manual-test.md E 节）。

**实现要点**：

- `TerminalEmulator.getSelectionText()`（纯 Java，EmuTest 36→46 用例）：
  软换行行拼回一个逻辑行、行尾填充只在逻辑行末行剥除（续行行尾空格是真实内容）、
  宽字符尾格收拢到头格、组合字符随主格保留（不做 NFC 合成）；同节的
  `wordSelectionAt()` 提供长按选词的词边界扫描（空白 / 标点 / 宽字符逐字，
  词可跨软换行），同样纯 Java、可桌面回归；
- 锚点用**全局行号 = 逐出计数（`evictedRows`）+ 绝对行号**，`clearScreen`
  也计入逐出，保证只增不减——新输出挤出 scrollback 时选区不漂移，
  被逐出部分自动裁掉（xterm 语义）；
- `TerminalView`：长按即按词选中（词内抖动保持整词，拖出词外再按字符扩展）
  → 拖动扩展（跨屏幕与 scrollback）→ 拖到上下边缘自动滚动（40ms/行，选区
  端点跟随新进入视口的内容延伸）→ 自绘浮动条（复制 / 全选 / 取消，不用
  ActionMode）。

**边界（对照 xterm Selections / VTE / Windows Terminal / Termux 核实）**：

- Shift 覆盖鼠标上报（xterm「shift override」）：程序开鼠标上报时，硬件
  键盘 Shift+按下/拖动走本地选区；触屏无 Shift，触摸归程序不变。
  **实机待测**（adb 无法模拟带 META_SHIFT 的触摸，manual-test E7）。
- 清除时机：单击清选区（不弹键盘）；任意按键/粘贴弃选区（xterm：key
  press discards selection）；复制后结束选择态（Termux 惯例）。
- 不做：双击选词、三击选行（「点终端=弹键盘」与之冲突）、系统放大镜
  （安卓放大镜绑定原生文本框，终端自绘内容用不上）、键盘 Shift+方向选择。
- 已做（2026-11 发布收尾补齐）：选区两端**自绘手柄**（水滴形，拖拽微调边界；
  触点先抬高 `HANDLE_STEM_DP + HANDLE_RADIUS_DP` 再取格，避免手指遮挡边界格）；
  浮动条**跟随选区**中点，上方空间不足时自动翻到选区下方（原为固定顶部）。
- 长按选词口径（2026-11-26）：空白分隔、标点各成一词（`/data/local/tmp` 长按
  选中 `local` 这样的路径片段）、CJK/emoji 逐字成词；词可跨软换行。词内轻抖
  保持整词（真实手指必然抖动），拖出词外才改按字符扩展。
- 应用菜单不在终端长按上（入口 = 长按键条「⌨」或顶栏「⋮」）；
  鼠标上报模式下终端长按无本地动作（实测确认）。

**遗留**：手感类复核项在 manual-test.md E8（长按时机、滚动速度、
浮动条遮挡观感）。

## 二、OSC 52 写剪贴板 —— 已完成（2026-11，实机验证过）

让 vim 的 `"+y`、tmux 的 copy-mode 写入系统剪贴板。前置（第一节选区）
完成后随即落地，实机 adb 全链路验证（写入 → 粘贴回读一致；关闭后写入被
拦，输入法剪贴板栏第三方位证）。实现细节见 internals.md「OSC 52 写剪贴板」。

**定稿边界逐条落地**：

- `handleOsc` 先拦 `52;` 前缀再走颜色查询分支；OSC 缓冲 64 → 100KB，
  超长序列置 overflow 标志整体丢弃（半截 base64 是垃圾）；
- 解码用 `java.util.Base64.getMimeDecoder()`（minSdk 26，零依赖成立，
  容忍发送方夹换行）；解码后 > 64KB 截断；
- 只支持 `c` 目标；`c2`/`sc` 忽略；`?` 读请求不应答（只写不读）；空数据忽略；
- `TerminalEmulator` 保持纯 Java：出口走 `ClipboardSink` 回调
  （Emulator → TermSession → Activity），策略层在 Activity——
  prefs `osc52` 菜单开关默认关 + 前台判定（UI 线程 `hasWindowFocus`）；
- EmuTest 55 → 66 用例（本节 11 例）：基本写入 / ST 终止 / 目标过滤 / 读请求 /
  空数据 / 坏 base64 / MIME 宽容 / UTF-8 往返 / 64KB 截断 / 超长丢弃 /
  丢弃后恢复 / 其它 OSC 不回归。

**编辑器侧前置条件（2026-11-27 实机定性，别再当应用缺陷查）**：Vim 的
`+clipboard`/`+xterm_clipboard` 只代表 **X11** 剪贴板能力，不代表会向终端发 OSC 52；
容器无 X11/`DISPLAY` 时 `"+y` 的 `+` 寄存器为空，应用端收不到任何序列（普通 `yy`
写 `0` 号寄存器正常）。`set clipboard=unnamedplus` 只是改默认寄存器，补不出提供方。
可用路径：Neovim 0.10+ 配 `vim.g.clipboard = 'osc52'`（Jammy 仓库 0.6.1 与 stable
PPA 0.7.2 都过旧，需 `ppa:neovim-ppa/unstable`；`nvim --clean` 会忽略该配置）。
详见 [manual-test.md](manual-test.md#f3-vim-yy根因已定位neovim-方案已验证2026-11-27m2010j19sc)。

## 三、多标签会话 —— 已完成（2026-11）

会话 id 采用**根进程 pid**（用户建议，评估后采纳）：

- pid 由内核保证存活期内唯一，logcat/adb 调试时 id 与 ps 直接对上；
- 代价是「start() 成功前 id 不存在」——会话表改为先 spawn 再入册，
  start 失败则无 tab（本来也没有可展示的会话）；
- pid 会复用，但 tab 退出立即摘表（onExit 同步移除），复用无从撞上。

身份与状态分离：`Tab { session, mode, container }`，`mode` 从全局状态
降级为 tab 属性；「同类 tab 已存活就切换贴屏，绝不暗杀别的 tab」是
切换的唯一语义，restart 只精确作用于目标 tab（重启单个会话不波及同类）。
UI：模式 chip 下拉即会话列表（`●` 标当前）+ 新建本地/容器入口；
`startContainer` 的 drop 已改成显式的用户动作（容器管理里的启动/停止）。

## 五、Intent 外部调用（`am start -a RUN_COMMAND`）—— 不做

外部应用可注入命令到终端，是安全事故面；Android 11+ 还要处理包可见性与
调用方白名单。没有明确的自动化诉求之前不引这个口子。
若将来做：仅 local 模式、仅显式声明的调用方、每次弹确认。

## 六、rootfs 换 Debian/Ubuntu —— 已解决前置障碍（2026-11：rootfs 移出 APK）

体积顾虑已消除：APK 不再内置任何 rootfs（原 Alpine pack ×3 ABI ≈ 10MB，
移出后 APK 10.93MB → 512KB）。镜像统一由用户获取：应用内 `docker pull`
（Alpine 官方源，泛化见第八节）或导入 docker save / export 的 tar，容器再从镜像物化；
**在册容器初始为空**，首次进容器模式弹引导。

因此换发行版的代码层障碍本来就为零（`ContainerBootstrap` 与发行版无关），
现在连体积障碍也没了——想用 Debian 就导入 Debian rootfs，不需要改 Java。
`scripts/fetch-runtime.*` 只准备 proot（rootfs pack 仅 `WITH_ROOTFS=1` 的
离线调试场景）。

## 八、docker pull 泛化到 Docker Hub —— 已完成（2026-11，实机验证过）

包体积优化后 `docker pull` 成了镜像唯一的内置获取通路，而它只认 Alpine
官方源——「想用 Debian」的实际答案是去电脑上 docker save 再拷 tar，
这条弯路值得抹平。设计定稿与实现细节见 pull-registry.md：

- 分发收在 `Containers.pull` 内部（UI 与控制台共用）：alpine 版本标签走
  dl-cdn 快路径原样保留，其余引用走 `RegistryPuller`（匿名 token、
  manifest list 按设备 ABI 选平台、blob 边下边验 sha256、串行下载一层叠一层）；
- **只收 gzip / 未压缩 tar 层，拒 zstd**（native 解码器与零依赖、512KB
  两条硬约束冲突），遇 zstd 报错指路导入通路；
- 第一版不做：digest 引用、登录鉴权、续传；2026-11 增补公共第三方 registry
  （ghcr/quay 等匿名直连，见 pull-registry.md 第九节）；
- 同批修复 `TarGzExtractor`：下层实体文件覆盖上层绝对符号链接时不再顺链写到宿主
  `/bin`（真机表现为 EROFS），`TarTest` 24→25 用例；
- 硬链接兜底定稿（2026-11-27）：SELinux 禁 `link(2)` 不可绕，uutils 的 applet
  又要求 `/proc/self/exe` 文件名等于 argv[0]，符号链接必被判 `Security violation`。
  改为「uutils → 钉死 applet 名的脚本 / 其余 → 指向真身的符号链接 / 最后才拷贝」，
  `ubuntu:25.10` 从 1.3GB 降到 ~116MB、`busybox:latest` 4.2MB，代价是 uutils
  applet 每次多一个 `/bin/sh`（约 +4ms），详见 internals.md「镜像层解包」；
- 已知：ghcr.io 直连在大陆网络可能只有 1–5 KB/s，可把镜像域名（如
  `ghcr.nju.edu.cn`）当 registry 域名填；
- 纯判定逻辑（ref 解析 / 平台选择 / mediaType 白名单 / 换源归一化 /
  WWW-Authenticate 解析 / registry 端点选择）抽 static 纯函数，桌面
  `RegistryTest`（90 用例）回归；JSON 与流下载已实机验证；
- APK 增量≈0（512KB → 530KB，仍远低于旧基线 10.93MB）。

**镜像源（换源）**：官方 Hub 在大陆经常被 DNS 污染（实测 401 前就连接
超时），同批加了换源能力——Hub / Alpine 两路各自可配（菜单「镜像源设置…」
或 `docker mirror`），registry 端点指向镜像站，401 时按应答
`WWW-Authenticate` 的 realm 取 token（镜像站自报端点，**不依赖
auth.docker.io**）。实机：debian:12 经 dockerproxy.net 约 50s、
busybox 经 1ms / daocloud 45s / 23s、alpine 换清华源 12s，全部拉取成功。
详见 pull-registry.md 第八节。

配套统一（见「容器管理统一走 Containers 单一接口」提交）：活动容器落位
下沉 `Containers.remove`，控制台 rm 守卫对齐多 tab（RUNNING 真源），
默认容器名 `suggestName` 两入口共用。

## 九、外接硬件键盘中文输入 —— 已完成（2026-11-20，实机验证过）

打通「硬键盘 → 输入法 → PTY」：有外接全尺寸键盘且输入法界面可见时，视图改成普通文本
框语义（`TYPE_CLASS_TEXT`），字母交给输入法组词，`commitText` 只把这次提交的内容写进
PTY；输入法收起或用户显式退出接管时回到 `TYPE_NULL`，字母逐键直发。菜单
「键盘与输入法 → 外接键盘中文输入」给自动/始终/从不三档策略，自动档下双击 Shift 在组词与
字母直发之间切换。

评估阶段记下的两处代价，实测后都换了做法：

- 回车不再由应用抢判 composing。搜狗对硬键盘组词全程不调 `setComposingText`，
  应用侧根本看不到 composing 状态，「有组词才让路」这条规则无从生效。改成接管态把
  回车/空格/方向键等终端语义键全数交给输入法，空闲时输入法会用
  `InputConnection.sendKeyEvent` 原样退回来（实测退得干净：`\r`、`\t`、`\e[A`、
  `\e[H`、`\e[5~`、`\e[2~`、`\e[3~`、`\e` 全部照发），挂着拼音时由输入法自己处置
  （回车把拼音原样上屏、不带动命令执行；退格删拼音尾字母；`Esc` 例外——退回来送
  PTY 但组词不取消）。抢在输入法前面发 CR 的旧做法会留下挂在输入法里的拼音，
  下一行凭空冒出词。
- 残留拼音的可见性靠「输入法窗口可见」这个硬门槛兜住：窗口没弹出来就不接管，
  不存在盲挂组词。双击 Shift 切走时窗口收起，组词随会话重建一并清掉。

三条需求各自的落点：①链路 = 接管态判定 + `restartInput` + `commitText` 只送本次提交；
②形态切换 = 外接键盘存在时键条与辅助键盘隐退（既有 `updateChrome` 逻辑，本轮复验
拔插回归）、输入法接管字母，拔掉后辅助键盘与软键盘组词照常；③语言切换 = 双击 Shift
（安卓把 Ctrl+空格/Alt+Shift/Win+Space 收作系统级输入法切换快捷键，应用抢不到也不该抢；
搜狗对硬键盘的 Shift 单击、Ctrl+Shift、Alt+Shift、Shift+空格都不作中英切换，
所以这个开关只能由应用侧做）。

验证通路只认 `tools/hardkey.c`（uinput 真实设备路径）；`input keyevent` 与
`--es keytest` 是虚拟键盘事件，输入法不接管，属假对照。批量动作用
`tools/ime-check.sh`，它会把接管态拉起来再逐条注入。

## 十、可访问性虚拟节点 —— 已完成（2026-11-26，实机验证过）

只读、按**可见逻辑行**暴露节点，服务于读屏与文本级 UI 自动化：`uiautomator dump`
现在能读到终端文本，MainActivity 拆分所需的自动化兜底随之成立。

**实现要点**：

- `TerminalEmulator.getLogicalLineText()` / `isWrappedContinuation()`（纯 Java，
  EmuTest 66→69）：沿 `wrapped` 链合到一行，行尾填充只剥逻辑行末行；空白行返回空串；
- `TerminalView.RowNodeProvider`：虚拟 id = 逻辑行在视口里的起始行，折行续行不重复
  建节点、bounds 覆盖该逻辑行占用的可见行；空白行不建节点；节点文本按逻辑行口径；
- 触摸探索：`dispatchHoverEvent` 聚焦命中行（续行归到逻辑行起点）；滚动 / 新输出 /
  尺寸变化发 `TYPE_WINDOW_CONTENT_CHANGED`（300ms 节流，且在仿真器锁外发送）；
  全部懒生成、不缓存，滚动 / 转屏 / 字号变化后自然按新视口重算；
- 只读：不做节点写操作、不模拟点击、不暴露全量 scrollback。

**实机验收**：35 列 `seq -s. 1 80` 的 239 字符长行在 dump 里是**一个**节点
（bounds 跨 6 行）；转横屏后文本不变（bounds 跨 2 行）；上滑后节点跟随视口
（首节点 561→483）；空白行无节点；`input text` 输入与回显不受影响。
**遗留**：TalkBack 朗读「不把折行读断」需人耳复核（设备已装 TalkBack；见 manual-test E13）。

## 十一、边界评审归档：已判不做（2026-11-26）

本表是「不做」结论的汇总入口，防止旧题重议；有独立章节的条目只在表里留一行。
「重评触发」为空表示保持不做，除非出现新的实测证据。

| 条目 | 判定的理由 | 重评触发 |
|---|---|---|
| 双击选词 / 三击选行 | 单击已被「点终端 = 切键盘」占用，双击与之冲突；长按选词覆盖主要场景（第一节） | 有明确诉求，且能给出与单击不冲突的成对手势 |

## 十二、镜像拉取的后台策略 —— A 已做、B 缓做（2026-11-26）

拉取镜像曾经用全屏 scrim 独占前台（几十秒不能切会话），而下载本身一直在后台线程。
本轮把「进度呈现」与「任务执行」分开处理，并评了「切出应用继续下载」的必要性。

**A. 应用内非模态（已做，857e23b）**

- 进度改为顶栏下方 `progress_strip` 一行（进度圈 + 文案），拉取 / 导入 / 创建三处共用；
  全屏 `overlay` 只留给「启动容器」（需短暂独占接 PTY）；
- 拉取与 tar 导入走独立执行器 `dualterm-io`，不占 `background` 单线程队列，
  下载/解包期间启动容器不排队；两者同线程也避免并发改镜像注册表；
- `pulling` 集合防同一 tag 重入；未注册镜像不进列表，不会基于半成品建容器；
- 生命周期：`onDestroy` 仅在 `isFinishing` 时中断；转屏/Activity 重建拉取继续；
- 中断兜底：镜像注册是最后一步，中途被杀只留 ORPHAN 目录，下次拉取自动清理
  （不是「不可用镜像」）。

**B. 前台服务（缓做，不做进本版本）**

- 增量：切到其它应用 / 锁屏后继续下载，并用通知反馈进度与结果；
- 成本：FGS（targetSdk 34 必须声明 `dataSync` 类型）、通知渠道、`POST_NOTIFICATIONS`
  运行时权限及被拒降级、进程级任务注册表与 UI 重附着；`Containers.pull` 的进度回调
  不能再绑 Activity；
- 维护面：Android 14/15 对 FGS 类型/时长持续收紧，而拉取是偶发操作；
- 失败代价低：一次中断 = 一次重试（分钟级），无数据损坏。

**取舍结论**：缓做。A 已覆盖「拉取时继续用 app」的主场景；B 等真实需求出现再上。
廉价替代方案（不做服务）：回前台时若发现「有拉取记录但进程已重启」，提示一次
「上次拉取已中断，可重试」——只告知不续跑，需要时再加。

**重评触发条件（任一命中）**：

1. 真实使用中累计 ≥2 次「切出去/锁屏导致拉取被系统杀掉」；
2. 导入 `docker save` 的 100MB+ 镜像成为常态；
3. 出现其它需要 app 代办的长任务（如容器内批量装包）。

**若开工的最小规格**：FGS(`dataSync`) 仅在拉取/导入期间存在；低优先级静默通知，
进度按 1s 节流；进程级 `PullRegistry` 供 UI 重新附着；完成/失败转普通通知并
`stopForeground`；通知权限被拒时静默回退 A（不阻止拉取）。

## 十三、容器管理界面改造：镜像/容器父子列表 + 属性页 —— 已完成（2026-11-28）

原状：一个 `AlertDialog` 里平铺「N 个容器 + M 个镜像」，两类对象混排，只能靠
「镜像」两字前缀分辨；新建在顶、拉取/导入/换源在底，列表一长就要来回滑。

**三个候选**：

| | 做法 | 代价 |
|---|---|---|
| A | 拆成「容器管理」「镜像管理」两个菜单入口 | 两个入口都要各点一遍才知道自己在哪；镜像→建容器跨入口 |
| B | 一个底部面板，容器 / 镜像两个页签 | 页签把父子关系抹平：切到容器页看不见它属于哪个镜像 |
| C | 独立的管理 Activity（整页） | 打断终端上下文；返回栈多一层；终端场景下过重 |

**第一版按 B 落地（当日上午），下午改判。** 镜像与容器是目录/父子关系——容器
必然由某个镜像物化而来，两个平级页签反而把这个事实藏起来了：切到容器页只能靠
副标题里的镜像名反推归属，切到镜像页也看不见它下面挂着谁。最终形态是
**单列可展开的父子里表**（仍属 B 的变体，记为 B′）：

```
容器与镜像                    控制台  完成
▼ alpine:3.21                    ⋯
    7.7MB · 1 个容器
    │ ★ c1                        运行中
▶ eclipse-temurin:17-jre         ⋯
    189MB · 无容器
              [＋]新建 [↓]拉取 [▤]导入 [⇄]换源
```

- 父行＝镜像：`▶/▼` + 名字 + `大小 · n 个容器`，整行点击展开/折叠；行尾 `⋯`
  进镜像属性页（不给整行第二种语义，避免「想看属性结果把列表收起来了」）；
- 子行＝容器：缩进 + 左侧竖线，只写名字与运行状态——镜像名父行已经写了；
- 没有容器时箭头恒为 `▶` 且点击不响应，不留「▾ 打开却是空」的错觉；
- 从「零容器」变成「有容器」时自动展开（新建/拉取完就看得见），此后尊重用户
  的折叠选择；
- 兜底分组「其他容器」：`image` 字段指向已不存在的镜像时单独成组，不让容器
  在界面里凭空消失（正常流程 `Containers` 会拦住删镜像，但旧数据可能例外）。

**为什么不做左右两列**：手机竖屏 360dp 一分为二，每列 180dp，
`eclipse-temurin:17-jre` 这种名字必然截断到无法辨认。父子里表在同一屏里就能
同时看到层级与内容，比双列或「点进去再返回」都省一次导航。

**实现**：`ui/ContainerSheet`（父子里表 + 操作栏）、`ui/ContainerDetail`
（属性页）、`ui/BottomPanel`（贴底弹层容器）。

**依赖撤回**：第一版为了页签与列表引入了 AndroidX / Material，按当晚落地的
准入规则（见硬约束 1）这三个库都属于「只取部分能力」，已全部移除。父子结构
本来就不需要页签，`MaterialButtonToggleGroup` 随之消失；列表最多十几条，
`RecyclerView` 的回收能力用不上，改 `ScrollView` + `LinearLayout` 手填；
`ContextThemeWrapper` 换回 Framework 的同名类。Release 从 1,992KB 回到 526KB。

**边界**：

- 列表只留必要信息，占用体积 / 存储路径 / 创建时间 / 引用关系进属性页——
  属性页底部就是同名操作按钮，少一次「长按出菜单」的心智负担；
- 镜像被容器引用时「删除镜像」直接置灰（`ColorStateList` 让危险色在 disabled
  时退回灰），不再让人点进去吃一遍报错；
- 不做 C：终端应用的主界面不该被管理功能打断；
- 菜单（`ui/MenuSheet`）仍是自绘。按硬约束 1，要迁到 Material 就得整个 App
  的菜单/对话框/键盘一起 Material 化（那才叫深度使用），不能只为菜单进货；
  这件事留作独立评估，不在本次范围内。

## 十四、会话下拉瘦身 + 快速访问栏自定义 —— 已完成（2026-11-28）

### 会话下拉：三个固定项压成一行图标

原状：模式 chip 下拉是系统 `PopupMenu`，前面 N 行会话，后面固定三行
「＋ 新建本地 Shell」「＋ 新建容器会话（容器名）」「容器与镜像…」。会话越多，
越要先滑过这三行才能看到全部会话——列表的屏幕空间被「每次都一样」的入口吃掉。

三个候选：

| | 做法 | 代价 |
|---|---|---|
| A | 三行不变，只把顺序调到最前 | 没解决问题，还是占三行 |
| B | 合并成一个二级菜单项（「新建 / 管理 ▸」） | 每个动作多一次点击；级联窗口在本应用里是已知的坏体验（见 `MenuSheet` 的注释） |
| C | 三行压成一行图标 | 图标需要一套规范，且要能认出来 |

选 **C**，并把「图标不能是随手画的」当成前置条件，于是有了 `ui/Icons` 与
`docs/dev/internals.md` 的「图标方案」：24×24 网格、描边 2、圆头圆角、
颜色运行时 tint（只两档）、尺寸只两档、一个语义一个图标。字形符号
（`⋮ ▶ ▼ ★ ← ⌨ ⛶`）不进这套体系——它们是排版记号，跟着字体缩放。

实现上顺手把 `PopupMenu` 换成自绘 `PopupWindow`（与 `MenuSheet` 同一套外壳：
`menu_bg` 圆角描边、44dp 行、按锚点上下空间决定弹出方向）：系统菜单没法塞进
一个「带图标的动作行」，也没法把动作行钉在滚动区之外。现在会话区滚动、动作行
固定在底部，第 30 个会话也能一眼看到三个入口。

顺带：容器面板的操作栏同步换成图标 + 极短文字（`＋` `↓` `▤` `⇄` 四个动作挤
一行，纯文字要 8 个汉字宽）。这是「多处使用」的第二个落点，也是图标规范
先落地再铺开的原因。

**为什么不是「退化图标就等于不要文字」**：纯图标只用在成组、且组内语义互斥的
地方（终端窗口 / 箱体 / 层叠）。能写全词的地方一律不退化——菜单项、属性页按钮、
空态说明都还是文字。纯图标入口给 `contentDescription`，再补一条长按提示。

### 快速访问栏：只选键，不做键

辅助键盘全收起时只剩那一行（`key_row`），即「快速访问栏」。它原本是写死的
9 个文字键 + `⌨` `⛶`。

三个候选：

| | 做法 | 代价 |
|---|---|---|
| A | 保持写死 | 每个人的高频键不同：写 vim 的要 `ESC`，跑构建的要 `^C`，用 tmux 的要 `^B` |
| B | 允许自由定义每个键（复用辅助键盘的步骤序列） | 与「自定义键」重复造第二套数据模型；栏只有一行，键一多就挤成牙签，宏键也放不下标签 |
| C | **从键目录里选 + 排序**，键行为固定 | 目录之外的键放不进来（可去辅助键盘用） |

选 **C**：这一行回答的是「哪些动作要在一屏之内够得着」，是选择题不是造键题；
要造键走辅助键盘的自定义键，两套机制不重叠也不共享数据。

规则：

- 目录 14 项：`CTRL` `ALT` `ESC` `TAB` `^C` `^D` `^L` `^R` `^U` `^Z` `←` `↑` `↓` `→`；
- 顺序即左右，编辑器里 `↑`/`↓` 调序，改动即时生效（键条就在对话框后面）；
- 上限 9 个：再多每格写不下 `CTRL`/`TAB` 这种四字母，这是键宽约束不是功能主张；
- `⌨` 常驻行尾、不占名额、不可删——它是辅助键盘的唯一入口；
- `⛶` 可关（全屏还有菜单与返回键两条路），关掉后其余键均分整行；
- 配置存成 `"CTRL,ALT,...|1"` 一条 prefs 字符串，认不出的 id 丢弃，整条空掉
  退回默认——prefs 被改坏不该让键条空成一条线。

**没做「拖拽排序」**：零第三方依赖的前提下自绘拖拽（长按浮起、跨位插入、
滚动跟随）成本远高于收益，而 `↑`/`↓` 在 9 个位置上最多点 8 次。

## 十五、会话下拉的宽度与高度 —— 已完成（2026-11-28）

### 宽度：跟内容，但按屏幕比例封顶

原状：面板宽度实际由最长会话标签决定（`setMinimumWidth(230dp)` + 行内
`maxWidth = 屏宽 - 60dp`）。容器会话的标签是
`容器 · eclipse-temurin:17-jre · pid 1234`，一长就把面板顶到接近整屏宽——看着像
抽屉，不像从 chip 上掉下来的一块菜单。

三个候选：

| | 做法 | 代价 |
|---|---|---|
| A | 固定一个比例（如 72%） | 只有一两个短会话时，右侧留一大片死白，同样「不像菜单」 |
| B | 纯自适应内容 | 容器名长时又回到近整屏宽 |
| C | **自适应内容 + 比例上限** | 长标签必被省略号截断（可接受，完整容器名在属性页/终端标题里） |

选 **C**，三段式：

```
自然宽 = max(最长会话行, 动作行)
下限   = 动作行实测宽（三个 44dp 图标 + 间距，不让图标换行）
上限   = min(屏宽 - 24dp, 屏宽 × 0.68)
```

下限不再拍一个 `230dp`，而是量动作行——真正的约束是「图标排不下会换行」。
实测（360dp 竖屏）：单会话面板 172dp（约 44% 屏宽），不再是近整屏。

### 高度：行数上限 + 滚动，上限可配

原状：会话多则面板一直长，只受「锚点上下可用空间」兜底。会话是长列表，
窗口高度不该由会话数量决定。

做法与辅助键盘的「最多几行」同构（`soft_kbd_max_rows`）：

- 会话区最多 `session_rows_max` 行，默认 8，`0` = 不限；
- 超出部分在会话区竖向滚动，动作行始终钉在面板底部；
- 实际高度 = `min(内容高, 行数上限 × 44dp, 锚点上下可用空间)`，哪一档先到就在哪滚；
- 入口：菜单「会话」组 →「会话列表行数：最多 8 行（超出滚动）」。

**限高带来的新问题**：当前会话排在第 5 行时，一打开只看见前 3 行，等于「打开
面板找不到自己在哪」。所以加了一条：打开时若当前会话不在可视区，把会话区滚到
它居中偏上。判定不解析标签里的 `●` 前缀（那是宿主的显示格式），改由
`Host.activeIndex()` 给出下标。

### 实现与边界

- 宽度与高度都在 `ui/SessionPicker`（`WIDTH_RATIO`、`ROW_H`），宿主只提供
  `maxVisibleRows()` 与 `activeIndex()`；
- 行高 44dp 只写一处（`ROW_H`），限高、可见行数、滚动定位都按它折算；
- 滚动条不开（`setVerticalScrollBarEnabled(false)`）：会话数一般在个位数，
  滚动条比它提示的信息更抢眼；能在滚动区里露出半行时，用户自然会滑。

## 十六、应用菜单是否 Material 化 —— 评估中（未开工）

现状：`ui/MenuSheet` 是自绘 `PopupWindow`，7 组两层、同窗口内切层、返回键逐层退、
按锚点上下空间决定弹出方向、超高可滚、整行 48dp 可点。

如果改用 Material（`PopupMenu` 或 Material3 的 `Menu` + `MaterialToolbar`），
下面这些是**真正会牵连到的地方**，不是菜单自己换个控件那么简单：

| # | 牵连点 | 具体后果 |
|---|---|---|
| 1 | **主题** | Material 组件要求 `Theme.Material3.*`。换主题是全局的：`Button` 自动变成 MaterialButton（默认 `minHeight=48dp`＋inset），键条现在 40dp 高、11sp 单行，会被撑形；所有 `AlertDialog`（行数/字号范围/粘贴确认/root 授权等十余处）换成 Material 样式；对话框里的 `EditText` 变成带下划线的 Material 输入框；`Spinner`（步骤模式）样式跟着变。等于一次全 App 视觉迁移 |
| 2 | **二级层级** | `PopupMenu` 的子菜单是级联窗口：点不回去、也接不住返回键。要么保留自绘，要么放弃 7 组改成 19 项平铺——而横屏 360dp 高度放不下 19 项，正是当初分组的理由 |
| 3 | **菜单数据模型** | `Group(title, labels[], ids[])` 要扩成带 icon / enabled / checkable / subtitle 的结构，`onMenuAction(int)` 的 19 路分发要重做；现在菜单项是纯文字，不涉及图标 |
| 4 | **方向与对齐** | `PopupMenu` 没有 `showAsDropDown(anchor, x, y, gravity)`，⌨ 长按（锚点在屏幕最底部）时向上翻的边距不可控；现在按 `spaceBelow/spaceAbove` 精确判断并选方向 |
| 5 | **体积** | material → appcompat + recyclerview + core 的依赖链。2026-11-28 实测过同样组合：Release 526KB → 1.9MB。按硬约束 1，这只有在「整 App 按 Material 组织」时才算合格 |
| 6 | **能免费拿到的** | TalkBack 的 menuitem 语义（现在自绘行被读作普通文本）、系统大字号下的自适应行高、Ripple、深浅色主题适配 |

**结论：本轮不动。** 功能性需求（两层、方向、滚动、返回）自绘已经满足，剩下的差距
主要是观感与无障碍语义；而成本的大头不在菜单，在第 1 条的主题全局迁移与第 5 条的
体积。触发条件：确实需要 Material You 动态取色、或需要标准 Material 对话框/输入控件
时**一次迁到位**（主题 + 菜单 + 对话框 + 键条 + 辅助键盘一起），开工前先解决键条
40dp 与 MaterialButton 48dp `minHeight` 的冲突，并复测 R8 后的体积。

不引依赖也能做的两处改进（目前都未做）：给菜单行补无障碍描述（Framework 没有
公开的 `role` API，只能靠 `contentDescription` 近似）；给面板加宽度上限——长标签
（「容器管理（N 个容器 / M 个镜像）」）在窄屏上现在会贴近屏宽。

## 硬约束（后续任何条目开工前先对一遍）

1. **第三方依赖的准入门槛是「深度使用」，不是「广泛使用」**：库本身要极广泛
   使用且有官方维护（AndroidX / Material 这一档），**同时**本项目必须对它有大
   面积需求——用它的控件体系、按它的设计规范组织界面，而不是只挑一两个类来
   省事。只取部分能力就引入，会让 APK 为一个面板背上整个库的体积，这是不可接
   受的。判断标准：把库里除了用到的那几个类之外的全删掉，本项目是否受损？答案
   为「不受损」就不该引。
   现状：**零第三方依赖**（`dependencies` 块故意留空）。2026-11-28 曾引入
   appcompat / recyclerview / material 做容器面板，当天即按本规则全部撤回：
   appcompat 只用了 `ContextThemeWrapper` 一个类（Framework 有同名类）、
   recyclerview 只服务一个十来条的列表、material 只用了两个按钮控件。
   撤回前后 Release 分别是 1.9MB / 526KB，差的 1.4MB 全是为「局部取用」付的账。
2. **`TerminalEmulator` 保持纯 Java**：桌面 EmuTest 是唯一的模拟器回归手段，
   引入 Android 类型等于放弃回归。
3. **APK 体积**：rootfs 已移出包（2026-11），零依赖后基线是 **533KB**
   （546,160 字节；撤依赖前一度到过 1.9MB，见上一条）。大头是三 ABI 各一份
   proot（jniLibs，约 397KB）。往 assets/nativeLibrary 塞任何东西都先算 ×3；
   图标是矢量（每个 300 字节级），别为省这点体积退回位图。
4. **会话层是多 tab**：会话 id = 根进程 pid，`tabs`（LinkedHashMap）是唯一
   会话表。动 `tabs` / `dropTabs` / `dropTab` / `SessionService` 前先读
   internals.md 的进程清理章节，确认不破坏 HUP → 补杀 → KILL 链；
   「切 tab 不杀会话」是不可回退的语义。
